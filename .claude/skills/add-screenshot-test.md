# add-screenshot-test

Add a Compose preview screenshot test for a screen so its rendered output is locked in as a reference PNG and CI fails on visual regressions.

## Required input

Ask the user (if not provided):

1. **Which screen** — e.g. `RecipeListScreen`. The screen lives in a feature `public` module and takes a Bloc interface.
2. **Which states to cover** — the loaded happy path is mandatory; surface other states the screen exposes that are visually meaningful (loading, empty, with-active-cooking-session, error, etc.). If a recent fix or new feature is the trigger, the state that exercises that code path is non-negotiable.
3. **Which form factors** — phone portrait (light + dark) is the default. Add phone landscape and tablet (`widthDp = 800`) if the screen branches on width via `PlusNavContainer` / `PlusNavRailHeaderContainer` or has bottom-anchored elements (FAB stacks, snackbars, bottom sheets) whose placement varies with available height/width.

## Where the pieces live

| File | Module | Purpose |
|---|---|---|
| `<Feature>Previews.kt` | feature `public` (commonMain) | **public** `previewXxxBloc` vals (fake Bloc implementations) + `internal @Preview` IDE preview functions |
| `<Feature>ScreenshotTest.kt` | `client/ui/screenshot-test` (`screenshotTest` source set) | `@PreviewTest @Preview @Composable` wrappers that call the screen with the public preview Blocs |
| Reference PNGs | `client/ui/screenshot-test/src/screenshotTestDebug/reference/...` | Generated by `updateDebugScreenshotTest`, committed to git |

The `screenshot-test` module is a **plain Android library** (not KMP) using Google's `com.android.compose.screenshot` plugin. KMP modules can't host the `screenshotTest` source set with `com.android.library`, so all snapshot tests are centralized here and depend on the relevant feature `public` modules.

## The pattern

### 1. Add `<Feature>Previews.kt` to the feature's `public` module

In `commonMain`, next to the `Screen` composable. Two halves:

- **Public** `previewXxxBloc` vals — fake `object : XxxBloc { ... }` instances returning `MutableStateFlow(model)` for `state` and `Unit` for handlers. **Public visibility is required** so the `screenshot-test` module can reuse them.
- **Internal** `@Preview @Composable` functions for the IDE preview pane. These don't run as tests; they just give the studio preview pane something to render.

Skeleton (real example: `client/cook/public/.../CookModePreviews.kt`):

```kotlin
package com.plusmobileapps.chefmate.<feature>

import androidx.compose.runtime.Composable
import androidx.compose.ui.tooling.preview.Preview
import com.plusmobileapps.chefmate.ui.theme.ChefMateTheme
import kotlinx.coroutines.flow.MutableStateFlow

private fun fooBloc(model: FooBloc.Model): FooBloc =
    object : FooBloc {
        override val state = MutableStateFlow(model)
        override fun onClick() = Unit
        // … return Unit for every handler on the interface
    }

val previewFooBloc: FooBloc = fooBloc(FooBloc.Model(/* loaded happy path */))
val previewFooBlocLoading: FooBloc = fooBloc(FooBloc.Model(isLoading = true))

@Preview(showBackground = true, heightDp = 1100)
@Composable
internal fun FooScreenPreview() {
    ChefMateTheme { FooScreen(bloc = previewFooBloc) }
}
```

The `Preview` import is `androidx.compose.ui.tooling.preview.Preview` — wired into every Compose KMP module by `ComposeConventionPlugin`, so no extra dep is needed in the feature's `build.gradle.kts`.

### 2. Wire the feature module into `screenshot-test`

In `client/ui/screenshot-test/build.gradle.kts`, add the feature's `public` module:

```kotlin
dependencies {
    implementation(project(":client:ui:public"))
    implementation(project(":client:text:public"))
    implementation(project(":client:cook:public"))
    implementation(project(":client:<feature>:public"))   // ← add

    screenshotTestImplementation(libs.screenshot.validation.api)
    screenshotTestImplementation(libs.androidx.compose.ui.tooling)
}
```

### 3. Add `<Feature>ScreenshotTest.kt` under `screenshotTest/`

Path: `client/ui/screenshot-test/src/screenshotTest/kotlin/com/plusmobileapps/chefmate/ui/screenshot/<Feature>ScreenshotTest.kt`.

Each case is a top-level `@PreviewTest @Preview @Composable fun` that wraps `ChefMateTheme { <Feature>Screen(bloc = previewXxxBloc) }`. The screenshot plugin discovers them by the `@PreviewTest` annotation (no JUnit runner involved).

Real example: `client/ui/screenshot-test/.../CookModeScreenshotTest.kt`. Skeleton:

```kotlin
package com.plusmobileapps.chefmate.ui.screenshot

import android.content.res.Configuration
import androidx.compose.runtime.Composable
import androidx.compose.ui.tooling.preview.Preview
import com.android.tools.screenshot.PreviewTest
import com.plusmobileapps.chefmate.<feature>.<Feature>Screen
import com.plusmobileapps.chefmate.<feature>.previewFooBloc
import com.plusmobileapps.chefmate.<feature>.previewFooBlocLoading
import com.plusmobileapps.chefmate.ui.theme.ChefMateTheme

// ── Phone portrait (default width, 1100 dp tall) ──────────────────────────
@PreviewTest
@Preview(showBackground = true, heightDp = 1100)
@Composable
fun FooPhonePortraitLightScreenshot() {
    ChefMateTheme { FooScreen(bloc = previewFooBloc) }
}

@PreviewTest
@Preview(showBackground = true, heightDp = 1100, uiMode = Configuration.UI_MODE_NIGHT_YES)
@Composable
fun FooPhonePortraitDarkScreenshot() {
    ChefMateTheme(darkTheme = true) { FooScreen(bloc = previewFooBloc) }
}

@PreviewTest
@Preview(showBackground = true, heightDp = 1100)
@Composable
fun FooLoadingScreenshot() {
    ChefMateTheme { FooScreen(bloc = previewFooBlocLoading) }
}

// ── Phone landscape (compact width <600dp, compact height) ────────────────
@PreviewTest
@Preview(showBackground = true, widthDp = 580, heightDp = 360)
@Composable
fun FooPhoneLandscapeScreenshot() {
    ChefMateTheme { FooScreen(bloc = previewFooBloc) }
}

// ── Tablet (medium width ≥600dp triggers responsive shell branch) ─────────
@PreviewTest
@Preview(showBackground = true, widthDp = 800, heightDp = 1100)
@Composable
fun FooTabletScreenshot() {
    ChefMateTheme { FooScreen(bloc = previewFooBloc) }
}
```

`@PreviewTest` only goes in `screenshot-test` — never in production modules, since it lives in a test-only artifact (`com.android.tools.screenshot.PreviewTest`).

### 4. Record reference PNGs

```bash
./gradlew :client:ui:screenshot-test:updateDebugScreenshotTest
```

PNGs land in `client/ui/screenshot-test/src/screenshotTestDebug/reference/com/plusmobileapps/chefmate/ui/screenshot/<TestClass>Kt/`. **Open each PNG and look at it** before committing — the framework happily records garbage if your preview Bloc renders wrong. Common things to verify:

- Theme colours look right in light and dark.
- Text isn't placeholder/lorem ipsum unless intentional.
- Bottom-anchored elements (FABs, snackbars, bottom sheets) sit where you'd expect — the screenshot canvas applies **no safe-area insets**, so anything that depends on a parent shell consuming insets (Scaffold's BottomAppBar, `PlusNavRailHeaderContainer`'s paddingValues) will sit flush at the canvas edge in the snapshot. That can be acceptable for visual-regression coverage but worth eyeballing.
- **Dark snapshots are actually dark.** If the screen doesn't wrap itself in `Surface(color = MaterialTheme.colorScheme.background)` (`CookModeScreen` does; `RecipeListScreen` doesn't), the canvas's white default leaks through under `@Preview(showBackground = true)` and you get a half-dark snapshot — header/text/colored components flip to dark theme, but the body background stays white. Fix in the test wrapper, not in production code: factor out a small `private fun <Feature>Screenshot(...) { ChefMateTheme(...) { Surface(color = MaterialTheme.colorScheme.background) { <Feature>Screen(...) } } }` and call it from every `@PreviewTest` in that file. See `RecipeListScreenshotTest.kt` for the worked example.
- Dialogs render — `AlertDialog` and `ModalBottomSheet` open into a separate window in the real app but composable directly into the canvas in screenshots. Cover them in a dedicated state preview if their layout matters.

### 5. Validate locally

```bash
./gradlew :client:ui:screenshot-test:validateDebugScreenshotTest
```

This is what CI runs (`screenshot-tests` job in `.github/workflows/tests.yml`). Diff reports upload as artifacts on failure.

## Reusable fixtures

If your preview Bloc needs realistic domain data, use the `<Type>.Sample` companion val convention rather than redefining fixtures per feature. `Recipe.Sample` (next to `Recipe.Empty` in `client/recipe/data/public/.../Recipe.kt`) is the worked example. Add similar `<Type>.Sample` companions on shared data classes when you need them.

For type-mapped UI items (`RecipeListItem`, etc.) where the production mapper lives in an `impl` module that the `public` module can't depend on, just hand-roll a small `private val sampleItems = listOf(<Item>(...), ...)` at the top of the previews file.

## Gotchas — do not skip

1. **Plugin is alpha and Android-only.** `com.android.compose.screenshot:0.0.1-alpha14` has no JVM/iOS targets. The screenshot-test module is `com.android.library` only; do not try to make it KMP.
2. **`@PreviewTest` is test-only.** Don't import `com.android.tools.screenshot.PreviewTest` from a production module — it's only on the `screenshotTestImplementation` classpath.
3. **Public visibility on preview Blocs.** `screenshot-test` lives in a different module, so `internal val previewFooBloc` won't compile in the test. Mark them `public` (the default) and put the `internal` only on the `@Preview` functions that exist for the IDE pane.
4. **No safe-area insets in snapshots.** The canvas has no `WindowInsets.navigationBars` / `displayCutout`. Code that conditionally consumes those insets renders the same as code that doesn't. If a fix is specifically about insets, the snapshot only catches *structural* regressions (e.g. someone re-adds a hardcoded extra padding), not inset-handling correctness. Document that limitation in the test if it matters.
5. **Preview Blocs return `Unit` for handlers.** Don't try to wire side-effects through them — the screen is rendered once, not interacted with.
6. **`compose.components.resources` is needed transitively.** Most feature `public` modules already pull it via the convention plugin, but if a fresh module's previews fail to resolve `Res.string.*`, check that `compose.components.resources` is in `commonMain.dependencies`.
7. **Don't share preview Blocs between features by re-exporting from `screenshot-test`.** Each feature owns its own previews file; the screenshot-test module just imports them.
8. **Cross-platform subpixel AA.** Mac arm64 and Linux x64 (CI) can produce 1-pixel-different antialiasing on FAB shadows / elevation edges, especially when the shadow lands on subpixel-misaligned coordinates at non-default `widthDp`. CI runs on Linux; if you record on Mac and CI fails on a handful of pixels in a shadow region, that's the cause. Mitigated module-wide by `screenshotTests { imageDifferenceThreshold = 0.001f }` in `client/ui/screenshot-test/build.gradle.kts` — a 0.1% pixel-diff budget that absorbs AA noise without masking real regressions (missing text, colour drift, layout shifts). If you still see CI failures with diffs concentrated in shadow/elevation regions, the threshold is your first lever — raise it cautiously, or copy the CI-rendered PNG from the `screenshot-test-report` artifact as the new baseline. Don't try to suppress with try/catch or pixel-tweak the PNG.

## Verification checklist

Before reporting done:

1. `./gradlew :client:<feature>:public:compileDebugKotlinAndroid` — confirms the previews file compiles.
2. `./gradlew :client:ui:screenshot-test:updateDebugScreenshotTest` — records references.
3. **Open every new PNG** under `client/ui/screenshot-test/src/screenshotTestDebug/reference/.../<TestClass>Kt/` and confirm the rendered screen matches expectations.
4. `./gradlew :client:ui:screenshot-test:validateDebugScreenshotTest` — re-runs the validator (must pass cleanly).
5. `./gradlew ktfmtFormat` — pre-commit hook runs this anyway.
6. Stage the `.kt` files **and** the new `.png` references in the same commit so CI's `validateDebugScreenshotTest` has the references it needs.
